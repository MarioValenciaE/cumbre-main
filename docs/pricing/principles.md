# Pricing Principles

> **Exploratory.** Cumbre has no approved prices, rates, or service catalog. Rates in any early pricing spreadsheet are experiments, not official prices. Do not invent final prices in documents or code.

## Philosophy

Price to cover real cost, reflect the value created, and keep Cumbre sustainable to maintain — without overselling technology the client doesn't need.

## Components to estimate for any project

| Component | Consideration |
| --- | --- |
| Founder time | Discovery, design, project management, delivery. Value it explicitly, even while the founders work unpaid |
| Development effort | Estimate in ranges; include testing, deployment, and handover |
| Technical uncertainty | Unknown data quality, undocumented systems, third-party APIs. Higher uncertainty → larger buffer or a paid diagnostic first |
| Direct costs | Licenses, contractors, tools |
| Infrastructure | Hosting, databases, AI APIs, messaging, storage. Prefer client-owned accounts or direct client billing |
| Contingency | Explicit percentage for scope surprises (to be decided) |
| Gross margin | Target margin to be decided |
| Client value | Estimated benefit (with stated assumptions) sets a ceiling on what is reasonable |
| Maintenance | Ongoing cost of keeping the solution working; offered as optional support |
| Scope exclusions | State clearly what is not included (extra integrations, training, data cleanup, third-party fees, changes after sign-off) |

## Commercial structure (hypothesis)

One-time implementation fee + client-owned infrastructure + optional recurring support. Possible future SaaS only if problems prove repeatable.

## Rules of thumb

- Show the assumptions behind every estimate.
- Prefer a small paid pilot or diagnosis when uncertainty is high.
- Never promise ROI figures Cumbre cannot support.
- Record any adopted pricing decision in [`PROJECT_CONTEXT.md`](../../PROJECT_CONTEXT.md).
